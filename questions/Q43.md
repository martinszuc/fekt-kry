# Q43 — Ideové návrhy kryptosystémov pre špecifické aplikácie

> [!summary] Čo je ideový návrh?
> Na skúške dostaneš zadanie (napr. „Navrhnite bezpečný systém pre elektronické voľby") a máš uviesť:
> 1. **Aké bezpečnostné služby** sú potrebné (dôvernosť, integrita, autentizácia, nepopierateľnosť…).
> 2. **Aké konkrétne algoritmy a protokoly** použiješ a **prečo**.
> 3. **Schéma komunikácie** (kto s kým, aké kľúče).
>
> Nie je nutné implementovať — stačí *zdôvodnený výber* s primeranou hĺbkou.

---

## 43.1 Autentizácia používateľov pristupujúcich vzdialene k serveru

**Kontext:** Používateľ sa prihlasuje k vzdialenému serveru cez verejný internet (napr. webová aplikácia, VPN, SSH).

### Potrebné bezpečnostné služby
- **Autentizácia entít** — overenie identity používateľa *aj* servera (obojstranná)
- **Dôvernosť** — prihlasovací token a relácia nesmú byť viditeľné útočníkovi
- **Integrita relácie** — parametre relácie nesmú byť pozmenené
- **Ochrana pred replay útokmi** — staré prihlásenie nesmie byť znovu použiteľné

### Navrhnuté riešenie

| Vrstva | Algoritmus/Protokol | Účel |
|--------|--------------------|----|
| **Transport** | **TLS 1.3** (ECDHE + [[concepts/ECDSA]]/[[concepts/EdDSA]]) | Šifrovaný kanál, autentizácia servera certifikátom |
| **Heslo na serveri** | **Argon2id** / scrypt | Bezpečné hašovanie hesiel — odolnosť voči GPU útoku |
| **2. faktor (MFA)** | **TOTP** (RFC 6238) + HMAC-SHA1 | Jednorazové kódy viazané na čas |
| **Identita servera** | **X.509 certifikát** s EdDSA/ECDSA | PKI — overenie, že server je legitímny |
| **Ochrana relácie** | **AES-256-GCM** (session token) | Šifrovanie session cookie |

**Schéma:**
```
Používateľ → TLS 1.3 handshake → Server (certifikát overí PKI)
Používateľ: heslo + TOTP kód
Server: Argon2id(heslo) porovná s uloženým hašom
Relácia: AEAD šifrovaný session token
```

> [!tip] Prečo Argon2 a nie bcrypt?
> Argon2id je víťaz Password Hashing Competition (2015). Je odolný voči **GPU aj ASIC** útokom — narozdiel od MD5/SHA1 (rýchle haše, 10 miliárd pokusov/s na GPU) a má nastaviteľné pamäťové nároky.

## 43.2 Komunikácia medzi senzormi a riadiacim systémom (IoT / Low-power)

**Kontext:** Senzory v priemyslovej hale posielajú dáta (teplota, stav) na riadiaci systém. Senzory majú obmedzený CPU, pamäť a batériu.

### Potrebné bezpečnostné služby
- **Integrita dát** — falošný senzor nesmie podvrhnúť hodnoty
- **Autentizácia pôvodu** — riadiaci systém musí vedieť, od ktorého senzora dáta pochádzajú
- **Selektívna dôvernosť** — niektoré dáta môžu byť citlivé
- **Nízka réžia** — minimálny čas CPU a pamäť

### Navrhnuté riešenie

| Komponent | Algoritmus | Dôvod výberu |
|-----------|-----------|-------------|
| **AEAD šifrovanie** | **ASCON-128** (víťaz NIST LWC 2023) | Navrhnutý pre IoT; 64-bajtový stav, 128-bit bezpečnosť |
| **Alternatíva s HW** | **AES-128-CCM** | Ak senzor má HW AES akcelerátor |
| **Kľúče** | **PSK** (Pre-Shared Keys) | Distribuujú sa pri výrobe/inštalácii — vyhnutie sa asymetrike |
| **Freshness** | **Sekvenčné čísla + nonce** | Ochrana pred replay útokmi bez nutnosti synchronizácie hodín |
| **Integrita bez dôvernosti** | **HMAC-SHA256** (truncated) | Ak šifrovanie nie je nutné, len autentizácia |

**Schéma:**
```
Senzor: ASCON-128(PSK, nonce, dáta) → Šifrovaná správa so seq. číslom
Riadiaci systém: Verifikácia ASCON tagu, kontrola seq. čísla
```

> [!warning] Prečo nie asymetrika?
> RSA/ECDSA operácie trvajú na 8-bitovom ATmega mikrokontroléri stovky milisekúnd a vyžadujú kilobajty pamäte. Pre senzor s 2 KB RAM je to neprijateľné.

## 43.3 Dôverný prenos multimediálnych dát v reálnom čase

**Kontext:** Videokonferencia, IPTV, bezpečnostné kamery — prenos real-time videa/audia cez sieť.

### Potrebné bezpečnostné služby
- **Vysokorýchlostná dôvernosť** — schopnosť šifrovať stovky Mbit/s bez latencie
- **Integrita** — detekcia podvrhu/úpravy streamu
- **Nízka latencia** — pridaná latencia < 1 ms (inak videokonferencia nefunguje)
- **Odolnosť voči strate paketov** — UDP protokol; chýbajúce pakety nesmú blokovať dešifrovanie

### Navrhnuté riešenie

| Vrstva | Protokol/Algoritmus | Dôvod |
|--------|--------------------|----|
| **Rámec** | **SRTP** (Secure RTP, RFC 3711) | Štandard pre bezpečný real-time prenos |
| **Šifrovanie** | **AES-128-CTR** (Counter Mode) | Paralelné šifrovanie, predvýpočet kľúčového prúdu, nezávislé pakety |
| **Autentizácia** | **HMAC-SHA1** / **AES-GCM** | Overenie integrity každého paketu |
| **Výmena kľúčov** | **DTLS-SRTP** (RFC 5763) | Výmena kľúčov cez UDP (nie TCP) |
| **Alternatíva** | **AES-256-GCM** + HW akcelerácia | Pre systémy s AES-NI inštrukciami (Intel/ARM) |

**Prečo CTR a nie CBC/GCM?**
- **CTR**: Každý paket šifrovaný nezávisle (nonce = číslo paketu). Stratený paket neblokuje ďalšie.
- **GCM**: Pridáva autentizačný tag, ale vyžaduje sekvenčné spracovanie tagu → vyššia latencia. Vhodné s HW akceleráciou.
- **CBC**: Chybné—strata paketu rozhodí celý ďalší stream (CBC chaining).

## 43.4 Generovanie kľúčov pre šifry AES a RSA

**Kontext:** Server potrebuje generovať kryptograficky silné kľúče pre AES šifrovanie a RSA páry kľúčov.

### Potrebné vlastnosti
- **Vysoká entropia** — kľúče nesmú byť predvídateľné
- **Odolnosť voči spětnému odvodzovaniu** — kompromitácia v čase $t$ nesmie odhaliť minulé kľúče
- **Certifikovaná implementácia** — súlad s FIPS 140-3

### Navrhnuté riešenie

```
[TRNG zdroj entropie]
     ↓
[Entropy pool] → [HMAC_DRBG / Hash_DRBG (NIST SP 800-90A)]
                         ↓
              [Kľúčový materiál pre AES/RSA]
```

| Komponent | Implementácia | Účel |
|-----------|--------------|-----|
| **TRNG** | Hardvérový zdroj (šum ADC, jitter oscilátora, kvantový šum) | Skutočná náhoda, zdroj seedu |
| **CSPRNG** | **HMAC_DRBG** (NIST SP 800-90A) | Deterministické roztiahnutie seedu, auditovateľné |
| **Pre AES-256** | 256 bitov z HMAC_DRBG | Priamo použiteľný kľúč |
| **Pre RSA-2048** | Miller-Rabin test prvočíselnosti | Generovanie veľkých prvočísel $p, q$ |
| **Certifikácia** | **FIPS 140-3** (Level 2+) | Povinné v regulovaných odvetviach |

> [!example] Linux entropy pool
> `/dev/random` (blokujúci, čaká na entropiu) a `/dev/urandom` (neblokujúci, seedovaný CSPRNG). V Linuxe 5.18+ je `/dev/random` a `/dev/urandom` ekvivalentných bezpečnosť — oboje používajú ChaCha20-based DRBG.

## 43.5 Elektronické voľby (anonymita a zamedzenie opakovanému hlasovaniu)

**Kontext:** Online hlasovanie — každý oprávnený volič môže hlasovať maximálne raz, ale hlas musí byť anonymný.

### Navzájom si odporujúce požiadavky
```
Anonymita voliča ←←←←←→→→→→ Overiteľnosť oprávnenosti
     ↑                              ↑
Tajnosť hlasu        ↔       Nemožnosť dvojitého hlasovania
```

### Navrhnuté riešenie — kombinácia primitív

**Krok 1 — Overenie oprávnenosti (slepým podpisom [[Q22]])**
```
1. Volič pripraví hlas m a OSLEPÍ ho: m' = m · rᵉ mod N  (r = náhodný faktor)
2. Volebná komisia PODPÍŠE m' → s' = (m')^d mod N
   (Komisia vidí len oslepený hlas — NEVIE obsah)
3. Volič ODLEPÍ: s = s' · r⁻¹ mod N
→ Výsledok: platný podpis Komisie na hlas m, bez znalosti obsahu
```

**Krok 2 — Anonymné odovzdanie hlasu**
- Hlas $m$ sa zašifruje pomocou **Elgamal / Paillier homomorfného šifrovania**.
- Odošle sa cez **anonymizačnú sieť** (napr. Tor) spolu s podpisom Komisie.

**Krok 3 — Sčítanie (homomorfné šifrovanie)**
- Šifrované hlasy sa sčítajú *bez dešifrovania* (Paillier kryptosystém: $\text{Enc}(v_1) \cdot \text{Enc}(v_2) = \text{Enc}(v_1 + v_2)$).
- Výsledok sa dešifruje len raz na konci volieb.

**Krok 4 — Zero-Knowledge Proofs (ZKP)**
- Každý volič priloží ZKP dôkaz, že hlas je v platnom formáte (napr. {0,1}) bez odhalenia hodnoty.

### Prehľad primitív

| Primitív | Funkcia |
|---------|---------|
| **RSA slepý podpis** | Komisia potvrdí oprávnenosť bez znalosti obsahu hlasu |
| **Paillier šifrovanie** | Homomorfné sčítanie hlasov bez dešifrovania |
| **ZKP (napr. Schnorr)** | Dôkaz, že hlas je v {0,1} bez odhalenia hodnoty |
| **Anonymná sieť** | Odpojenie IP adresy od hlasu |

## 43.6 Elektronická komunikácia občanov so štátnou správou

**Kontext:** Občan podáva žiadosť, odvolanie alebo iný právne záväzný dokument elektronicky.

### Potrebné bezpečnostné služby
- **Autentizácia** — úrad musí vedieť, kto podáva
- **Nepopierateľnosť** — občan nemôže poprieť podanie
- **Integrita** — dokument nesmie byť zmenený po podaní
- **Dôvernosť** — niektoré dokumenty sú citlivé (zdravotné, daňové záznamy)

### Navrhnuté riešenie

| Vrstva | Algoritmus/Štandard | Dôvod |
|--------|--------------------|----|
| **Podpis dokumentu** | **QES (eIDAS)** cez eID kartu alebo EUDI Wallet | Právna sila vlastnoručného podpisu ([[Q42]]) |
| **Formát podpisu** | **PAdES-LTA** (PDF Advanced Electronic Signature - Long Term Archival) | Archívny formát — platí aj po expirácii certifikátu |
| **Identifikácia** | **SAML 2.0 / OpenID Connect** s eIDAS atribútmi | Federatívna identita naprieč EÚ |
| **Dôvernosť** | **TLS 1.3** + **S/MIME / PGP** pre email | Šifrovanie prenosu a uloženia |
| **Časové razítko** | **RFC 3161** ([[Q17]]) | Dôkaz o čase podania |
| **Archivovanie** | **PAdES-LTA** s dlhodobým OCSP/CRL | Platnosť po desiatky rokov |

## 43.7 Komunikácia medzi bankou a vzdialené pobočky (Site-to-Site VPN)

**Kontext:** Centrála banky a pobočky v rôznych mestách — trvalé prepojenie sietí.

### Potrebné bezpečnostné služby
- **Dôvernosť** — ochrana bankového tajomstva
- **Obojstranná autentizácia** — obe siete sa navzájom overia
- **Perfect Forward Secrecy (PFS)** — kompromitácia dnešného kľúča nesmie ohroziť minulú komunikáciu
- **Auditovateľnosť** — logovanie pre regulátorov

### Navrhnuté riešenie

| Vrstva | Protokol/Algoritmus | Dôvod |
|--------|--------------------|----|
| **VPN tunel** | **IPsec** v tunelovom režime | Štandard pre site-to-site VPN, šifruje celé IP pakety |
| **Výmena kľúčov** | **IKEv2** s **ECDSA certifikátmi** | Vzájomná autentizácia pobočiek cez PKI certifikáty |
| **Šifrovanie** | **AES-256-GCM** (AEAD) | Najvyššia bezpečnosť + autentizácia v jednom prechode |
| **PFS** | **ECDHE** (*Ephemeral* DH) | Dočasné kľúče — kompromitácia master kľúča nič neodhalí |
| **Certifikáty** | **X.509 + interná CA** | Banka prevádzkuje vlastnú PKI hierarchiu |

**Schéma:**
```
Pobočka A          IPsec tunel (IKEv2 + ECDHE)          Centrála
[ECDSA certifikát] ←→ overenie ←→ [ECDSA certifikát]
                   AES-256-GCM šifrovaný tunel
```

> **PFS — prečo je kľúčové?**
> S ECDHE sa pre každú reláciu generuje nový dočasný kľúč. Útočník, ktorý dnes odchytí a uloží šifrovanú komunikáciu a zajtra získa dlhodobý kľúč banky, *nedokáže* dešifrovať minulé relácie — každá relácia má iný kľúč.

## Prehľadná tabuľka scenárov

| Scenár | Kľúčové primitíva | Hlavná výzva |
|--------|-------------------|-------------|
| **Vzdialená autentizácia** | TLS 1.3, Argon2, TOTP | MFA bez UX degradácie |
| **IoT senzory** | ASCON, PSK, seq. čísla | Nízka réžia CPU/pamäte |
| **Reálny čas multimedia** | SRTP, AES-CTR, DTLS | Latencia a strata paketov |
| **Generovanie kľúčov** | TRNG, HMAC_DRBG | Dostatočná entropia |
| **E-voľby** | Slepý podpis, Paillier, ZKP | Anonymita vs. overiteľnosť |
| **E-government** | QES, PAdES-LTA, RFC 3161 | Dlhodobá archivovateľnosť |
| **Bankové VPN** | IPsec, IKEv2, ECDHE, AES-GCM | PFS, obojstranná autentizácia |

## Callouts

> [!summary] Čo musím vedieť na skúšku
> Pre každý ideový návrh: **1) služby → 2) algoritmy → 3) schéma**.
> Kľúčové kombinácie spamäti:
> - Vzdialená autentizácia: **TLS 1.3 + Argon2 + TOTP**
> - IoT: **ASCON + PSK**
> - Multimedia: **SRTP + AES-CTR**
> - E-voľby: **Slepý podpis + Paillier + ZKP**
> - E-government: **QES + PAdES-LTA + RFC 3161**
> - Banka: **IPsec + IKEv2 + ECDHE + AES-256-GCM**

> [!tip] Ako si to pamätať
> **„ASPEG-B"** — Autentizácia, Senzory, Prúdové médiá, E-voľby, Government, Banka.
> Pre každý scenár: najprv napíš **„čo"** (služby), potom **„čím"** (algoritmy).

> [!warning] Častá chyba
> Na skúške sa nezdôrazňuje len správny výber algoritmu, ale **zdôvodnenie**. Prečo AES-CTR a nie AES-CBC pre streaming? (Odpoveď: strata paketu pri CBC rozbije celý stream; CTR každý paket nezávisle.) Zdôvodnenie = body!

> [!example] Príklad z praxe — Threema (E2E šifrovaný messenger)
> Threema implementuje bezpečnú komunikáciu podobnú scenáru 43.3:
> - Výmena kľúčov: **Diffie-Hellman** (X25519)
> - Šifrovanie správ: **NaCl/libsodium** (XSalsa20-Poly1305 = AEAD)
> - Identita: náhodné 8-znakové ID (nie telefónne číslo = anonymita)
> - Bez centrálneho ukladania správ (E2E = server nevidí obsah)

## Flashcards

Q:: Aké kryptografické primitíva by si použil pre bezpečnú vzdialenú autentizáciu?
A:: TLS 1.3 (šifrovaný kanál), Argon2id (hašovanie hesiel), TOTP / FIDO2 (MFA), X.509 certifikát s EdDSA/ECDSA (autentizácia servera).

Q:: Prečo sa pri IoT senzoroch nepoužíva RSA/ECDSA a čo sa použije namiesto toho?
A:: RSA/ECDSA sú príliš náročné pre obmedzený CPU a pamäť IoT zariadení. Namiesto: ASCON (lehkotonážny AEAD), PSK (Pre-Shared Keys) a sekvenčné čísla pre freshness.

Q:: Ako rieši homomorfné šifrovanie (Paillier) problém anonymity v e-voľbách?
A:: Paillier šifruje hlasy tak, že $\text{Enc}(v_1) \cdot \text{Enc}(v_2) = \text{Enc}(v_1 + v_2)$ — súčet hlasov sa vypočíta priamo nad šiframi bez dešifrovania jednotlivých hlasov. Výsledok sa dešifruje raz na konci.

Q:: Čo je Perfect Forward Secrecy a prečo je dôležité pre bankové VPN?
A:: PFS = každá relácia má dočasný (ephemeral) kľúč (ECDHE). Ak útočník získa dlhodobý kľúč, nedokáže dešifrovať minulé relácie (každá mala iný dočasný kľúč). Zabraňuje „ulož dnes, dešifruj po kompromitácii".
